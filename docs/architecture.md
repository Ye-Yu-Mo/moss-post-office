# 架构边界

这份文档记录几条**不随功能改动而变**的边界。新功能先对照这里，再决定写在哪一层。

## 1. 游戏循环在客户端，账号/存档在服务端

```
浏览器
  ├─ 游戏模拟（盖戳、订单、邮路、远行、月光树）
  ├─ localStorage（离线优先，断网也能玩）
  └─ 可选同步 → /api（同源，serve.py 反代）→ moss-sync（Rust / axum）
                     ├─ 注册、登录、会话
                     ├─ 云存档（不透明 JSON + revision）
                     └─ 事件上报
```

- 服务端**不跑游戏 tick**，不认识卡牌、订单或经济系统。规则只有一份，在前端。
- 存档是客户端生成的 JSON blob；服务端只负责鉴权、版本号和持久化。
- 网络失败不能阻塞游玩；同步失败时继续用本地存档，下次再推。

## 1.1 社交边界

镇口只做**元数据社交**：邮差榜、预设明信片、NPC 回信。

- 不存自由文本，减少审核和骚扰面；明信片正文是服务端固定的模板。
- NPC 是服务端种子数据，接口里明确标记 `kind: "bot"`，UI 显示「NPC」，不伪装成真人。
- 礼物是小额的 1–2 墨点/材料，由客户端领奖后写入本地存档；服务端只记录领取状态。不要把它扩展成可交易经济。
- 好友是双向关系：好友码申请 → 接受；好友档案只对好友开放，排行榜不暴露好友码。
- 后院菜地是服务端计时的轻社交：收菜/偷菜由服务端判定，奖励由客户端写入存档；不做资源交易。
- 不做实时聊天或自由信件；如果以后需要，另起服务并单独设计审核/限流。

## 2. Rust 后端：积木，不追大而全

- 当前 `moss-sync` 用 **axum + rusqlite** 自行组装，专注账号/元数据 CRUD。
- 不引入 colyseus-rs：我们没有实时房间、帧同步或状态广播。为了「以后可能」上房间而现在引入，只会增加耦合。
- 如果未来做联机（例如多人同图、实时协作分拣），**另起一个服务** `moss-realtime`：
  - 用 colyseus-rs 或 axum WebSocket 做房间/状态同步；
  - 只通过 token introspection 复用 `moss-sync` 的身份，不共享数据库表；
  - 实时循环与账号/存档 CRUD 分开部署、分开扩缩容。
- 依赖版本保守：`Cargo.lock` 提交；Rust stable；升级单独做，不和功能混在一起。

## 3. 前端：引擎与 UI 框架互不侵入

- 当前游戏是 **DOM/CSS 的卡牌 + 经营 UI**，不是精灵/场景游戏：
  - 不引入 Phaser：把订单、标签页、远征面板搬进 canvas 是倒退；
  - 不引入 React Three Fiber / Babylon：没有 3D 需求；
  - PixiJS 只负责环境粒子，可随时降级关闭。
- 如果未来出现真正的 2D 场景玩法（例如可走的地图小游戏），用 **Phaser 4** 做在**独立 canvas 容器**里，不接管现有 DOM UI；3D 才考虑 Babylon.js。
- UI 框架只做 UI：
  - 推荐 **Vue 3**（渐进、UI 密集、包体适中）用于面板/弹窗/账号界面；
  - 游戏状态放在框架外的 store + 事件总线，逐帧循环不进入框架的响应式系统；
  - 迁移按面板进行，不一次性重写；当前阶段保留原生 DOM 实现，新增复杂 UI 再引入 Vue。
- 构建：Vite + npm，Node 版本由 `.nvmrc` 固定（24），`package-lock.json` 提交。

## 4. 存档与同步语义

- 本地 `localStorage` 是离线时的唯一事实来源。
- 注册：把当前本地存档作为初始 revision 1 上传。
- 登录：以服务器存档为准；若服务器为空，则上传本地存档。
- 日常保存：本地立即写，云端防抖上传。
- 冲突（`409`）：不自动覆盖。玩家选择「云端覆盖本地」或「本地覆盖云端」。
- 服务端 revision 单调递增；不做字段级合并。

## 5. HTTP 部署的威胁模型

线上目前只能走明文 HTTP，所以认证不发送原始密码：

- 浏览器用 PBKDF2-SHA256（100k 轮）从 `密码 + 用户名` 派生 32 字节 verifier；密码只存在于浏览器内存。
- 注册发送 verifier；登录先取一次性 nonce，再发送 `HMAC-SHA256(verifier, nonce)`，proof 不能重放。
- 注册那一次仍会把 verifier 暴露在链路上；拿到它的人可以冒充登录。**首次注册尽量在可信网络完成。**
- Bearer token 仍然会被动可被窃听；拿到 token 就能读存档。30 天有效期是便利与风险的折中。
- 挑战应答防不了主动中间人：HTTP 页面和 JS 本身可被篡改。要真正解决，只能上 TLS（Caddy/Cloudflare Tunnel/平台 HTTPS）。

这些不是“HTTP 已经安全”，而是“在只能 HTTP 的前提下，避免密码明文和最直接的登录重放”。

## 6. 未来的链上收藏品（暂不实现）

如果以后真的要把资产上链，只考虑**装饰性收藏品**，不碰货币、进度和强度：

- 候选：镇口明信片、邮册纪念戳。它们已经有服务端记录（发送者、模板、时间、领取状态），可以作为「来源可验证」的收藏。
- 不能上链：邮票、墨点、材料、卡牌、遗物、远行进度。服务端目前不做权威游戏模拟，客户端存档可被改；把有强度的资产上链会立刻出现复制和作弊。
- 正确顺序：先让服务端成为收藏品发行的事实来源（现在已经在记 `postcards`），铸造资格由服务端签名；钱包只是接收端，不参与游戏循环。
- 钱包接入应使用签名登录（如 SIWE），不要接触助记词，不托管私钥；需要 HTTPS，当前 HTTP 部署不满足。
- 默认保留完全离线的非链上路径；链上只是可选展示/转让，不能成为玩法的前置条件。
- 合规、地区限制、年龄门槛和税务问题需要在上线前单独评估，尤其是面向中国大陆用户时。

## 7. 前端迁移状态（Vue 3）

- 2026-11-27：接入 Vue 3 + `@vitejs/plugin-vue`；`TownView.vue` 已接管整个镇口（好友 / 收件箱 / 广场），内部复用 `GardenPanel.vue`。
- 挂载方式：`mountTown.js` 在镇口 DOM 里创建/卸载 Vue app；props 是快照，事件通过回调回传旧逻辑；点击用 `.stop` 避免和旧事件委托重复触发。
- 游戏循环、存档、远征状态机仍然在 Vue 外；Vue 只读 UI 数据，不参与逐帧 tick。
- 迁移顺序：镇口（已完成）→ 账号 → 订单/邮册/月亮 → 远征/工坊；盖戳台保留原生或最后做薄包装。
- 当前 bundle 约 254 KB（gzip 89 KB），其中 Vue 运行时约 60 KB；迁移期间接受这个增量，完成后删除旧字符串模板会回落。
- 禁止：把逐帧循环、计时器或游戏状态写进 Vue 响应式；每个面板只接收不可变快照和回调。

## 7. 版本策略

| 层 | 策略 |
| --- | --- |
| Node | `.nvmrc` 固定 24；`engines >= 20` |
| 前端构建 | Vite 主版本锁在 `package-lock.json`，升级单独提交 |
| Rust | stable + `Cargo.lock`；axum 0.8 系列 |
| 数据库 | `PRAGMA user_version`；v1 匿名表迁移为 `*_v1_legacy`，不静默删除 |
| 游戏存档 | `state.version` 单调递增，加载时归一化并向后兼容 |
